[#features-dynamic-configuration]
= Dynamic Configuration

Dynamic Configuration is a code-first, selector-based alternative to <</basics/application-model,Application Models>> for configuring A12 Client applications.
Instead of defining regions, flows, scenes, and menus in static JSON files, you write them directly in TypeScript — enabling runtime-derived, state-dependent UI configuration.

[NOTE]
====
The Dynamic Configuration API is currently marked as `@experimental`. While it is functional and used in production applications, its API surface may still change in future releases.
====

== Setup

To enable Dynamic Configuration in your composable appsetup:

1. Use `withDynamicConfig()` in your feature composition.
2. Use `APPLICATION_MODEL_PLACEHOLDER` as the model (the traditional Application Model is not used, but the setup API still requires one).
3. Register your `DynamicConfiguration` modules with the <<module-registry,ModuleRegistry>>.

The root component of your application should use `DynamicRegionUi` (instead of the traditional layout/view providers) to render the region tree.

== Defining a DynamicConfiguration

A `DynamicConfiguration` module extends `Module` but replaces the JSON-based `model` and `views` properties with three new contributions:

* `regions` — the region/layout tree
* `flows` — flows containing scenes with match conditions and directives
* `menus` — menu entries with actions and i18n labels

[TIP]
====
The structure of these objects roughly follows the structure of the Application Model. This can be helpful when migrating an existing App Model to a Dynamic Configuration.
The main differences are described in the <<migrate-from-appmodels,migration guide>>.
====

Each of these can be either a plain object (static) or a Redux selector function `(state) => T` (dynamic). See <<features-dynamic-configuration-selectors>> for details.

== Defining Regions

Regions define the layout tree of your application. Each `DynamicRegion` has a `name`, a `layout` (a React component wrapped in a `LayoutNG` object), and optional `subRegions`.

* The root region by convention uses an empty string (`""`) as its name.
* Sub-regions are referenced by absolute paths (e.g. `"/CONTENT"`).
* Multiple modules can contribute regions — regions with the same name are merged automatically.

== Defining Flows and Scenes

Flows group related scenes. Each `DynamicScene` defines:

* `name` — a unique scene identifier
* `matches` — a `DynamicMatchCondition`: a function `(descriptor: Activity.Descriptor) => boolean` that determines when this scene is active
* `sceneChange` — contains `onEnter` and/or `onExit` arrays of directives
* `priorScene` (optional) — links to a preceding scene, establishing scene order within a flow
* `defaultCase` / `cases` (optional) — for sub-case handling within a scene

=== Directives

Scene changes use directives to modify the UI:

`DYNAMIC_ADD_VIEW`:: Adds a view component to a region. The component is referenced directly (not by string name). Optionally includes `models` (model descriptors) and `constraints`.
`DYNAMIC_CLEAR_REGION`:: Clears all views from a region. Optionally accepts a new `layout` to apply after clearing.

Unlike the traditional Application Model where views and layouts are referenced by name through a provider, Dynamic Configuration references React components directly — eliminating the need for a mapping of string constants to components (e.g., "viewProvider").

== Defining Menus

Each `DynamicMenu` has:

* `id` — unique menu identifier
* `label` — a `Localizable` object (typically an i18n resource key like `{ key: "application.menu.person" }`)
* `selected` (optional) — whether the menu item is currently active
* `action` (optional) — a callback `(dispatch: Dispatch) => void` that is invoked when the menu is clicked
* `children` (optional) — nested sub-menus

== Static vs Dynamic Configuration (Selectors)

The `regions`, `flows`, and `menus` properties on `DynamicConfiguration` accept the type `SelectorOrObject<T>`:

[source,typescript]
----
type SelectorOrObject<T> = T | ((state: object) => T);
----

**Static (plain object):** Use when the configuration is known at build time and does not depend on application state. This is the simpler option and has no performance concerns.

**Dynamic (selector function):** Use when the configuration depends on Redux state — for example, showing different regions based on active activities, or computing menu `selected` state from current activities.

== Performance and Memoization

When using selector functions, it is critical to ensure **referential stability**. The framework uses reference equality (`===`) to detect changes — if a selector returns a new object or function reference on every call, it triggers unnecessary re-renders even when the underlying data hasn't changed.

* Move non-dynamic parts out of the selector — use plain objects for anything that doesn't depend on state.
* Use a memoization utility keyed on the values that actually change.
* Ensure stable references for: match condition functions, React components, layout objects, and menu arrays.

== Caveats and Limitations

=== No `initialActivity`

Dynamic Configuration has no equivalent of `ApplicationModel.initialActivity`. If your application needs to start with a specific activity, you have two options:

* **Setup Actions** Dispatch the initial activity by putting in the setup actions of the application setup.
* **Deep linking configuration:** Combine with the deep-linking feature to derive the initial activity from the URL.

=== No Default Wrapping of View Components with Progress Indicators / Error Boundaries

Previously, views added via `VIEW_ADD` directives were automatically wrapped with a progress indicator and error boundary by the default A12 Client Layouts (like the `MasterDetailLayout`). These could be customized via the corresponding provider.

With Dynamic Configuration, you are responsible for the rendering of the layout / view components directly, which means that A12 Client by default will not do any wrapping in the default layouts. To restore this functionality, simply wrap your view components with Progress Indicator / Error Boundary components as needed (or move the logic in the view components themselves).

=== Deep Linking Interaction

The deep-linking system traditionally relies on `ApplicationModel.initialActivity` to determine the starting point. When using Dynamic Configuration, ensure you handle the initial navigation explicitly (see above).

=== Memoization is Required for Dynamic Selectors

Unlike Application Models (which are structurally compared), Dynamic Configuration uses reference equality. Forgetting to memoize selector return values can cause excessive re-renders. See <<Performance and Memoization>> for details.

=== No Direct `permission` Property on Menus

The `ApplicationModel.Menu.permission` property is not directly available on `DynamicMenu`. However, you can implement permission-based filtering in your selector logic by conditionally including or excluding menu entries based on the current user's permissions from the state.

=== Module Registration Order

When multiple modules contribute regions, the module that defines the root region structure (the application frame) should be registered first. Other modules contribute into the region tree established by the root module.
In the same way, contributed menus will be shown in order of their registration when using the default Menu component. If this is not wanted, provide a custom Menu component (see the A12 Client Devapp for an example).

== Comparison: Application Model vs Dynamic Configuration

The following table maps concepts from the traditional JSON-based Application Model to their Dynamic Configuration equivalents:

[cols="1,1",options="header"]
|===
| Application Model (JSON) | Dynamic Configuration (TypeScript)

| JSON `ApplicationModel` file
| `DynamicConfiguration` module (TypeScript object)

| `Module.model` (JSON selector)
| Removed (`never`) — configuration is code

| `Module.views` (string → component map)
| Components referenced directly in `DynamicAddView.component`

| `ApplicationModel.Region` + `Layout` (by name)
| `DynamicRegion` + `LayoutNG` (React component)

| `Flow` / `Scene` / `MatchCondition` (JSON)
| `DynamicFlow` / `DynamicScene` / `DynamicMatchCondition` (function)

| `Menu` with `initialActivity` + `label[]`
| `DynamicMenu` with `action` callback + `Localizable` label

| `Directive.Add` (`VIEW_ADD` by name)
| `DynamicAddView` (`DYNAMIC_ADD_VIEW`, direct component)

| `Directive.Clear` (`REGION_CLEAR`)
| `DynamicClearRegion` (`DYNAMIC_CLEAR_REGION`)

| `ApplicationModel.initialActivity`
| No direct equivalent — dispatch actions instead.

| View provider (`createViewProviderSelector`)
| Not needed — components are imported directly

| Layout provider (by string name)
| `LayoutNG` object with `component` property
|===

== Backward Compatibility

The `AppmodelToDynamicConfigurationAdapter` bridges traditional JSON Application Models into the Dynamic Configuration system. This allows existing modules using JSON models to coexist with new `DynamicConfiguration` modules in the same application.

The adapter is automatically registered when using `withAppModelAdapter` in your composable appsetup. It converts the loaded Application Model's regions, flows, and menus into their dynamic equivalents at runtime.

NOTE: This adapter is not meant to be used in production! It only serves as way to test DynamicConfiguration in an existing A12 Client application (using Application Models).

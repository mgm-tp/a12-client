= 2026.06-ext2

== Breaking Changes

=== Renamed Builders

The `withX` prefix now means one thing: install a feature, once. The two builders that only write a config value are renamed after what they do. Both keep their signature.

|===
| Old Name | New Name
| withReducerMap | addReducerMap
| withApplicationResetTriggers | setApplicationResetTriggers
|===

The naming convention is documented in the <</advanced/composeable_appsetup,composable appsetup>> chapter.

Required:: Depending on whether you used one of these builders.
Migration:: Manual, no codemod available.
Result::
+
[source,typescript]
----
// before
combineFeatures(withReducerMap(myReducers), withApplicationResetTriggers(myTriggers));

// after
combineFeatures(addReducerMap(myReducers), setApplicationResetTriggers(myTriggers));
----

=== withDynamicConfig Is Passed Directly

`withDynamicConfig` was the only feature that had to be invoked. It is now passed directly, like every other feature.

Required:: Depending on whether you use <<features-dynamic-configuration,Dynamic Configuration>>.
Migration:: Manual, no codemod available.
Result::
+
[source,typescript]
----
// before
combineFeatures(withModel(APPLICATION_MODEL_PLACEHOLDER), withDynamicConfig());

// after
combineFeatures(withModel(APPLICATION_MODEL_PLACEHOLDER), withDynamicConfig);
----

=== Type Parameter of the Builders Moved

The type parameter of the builders that take arguments sat on the outer function, which never used it. TypeScript resolved it to its constraint, so applying such a builder dropped the refinements the config already carried:

[source]
----
createA12ApplicationSetup(withModel(m)(withModelLoader(ml)(cfg)));
// TS2345: 'ApplicationWithConfiguredModel<A12ApplicationConfig<BaseConfig>>'
//         is not assignable to 'A12ApplicationConfig<Config>'
----

The type parameter now sits on the function that receives the config, where it is inferred. An explicit type argument on the outer call no longer compiles.

Required:: Depending on whether you passed a type argument explicitly.
Migration:: Manual, no codemod available.
Result::
+
[source,typescript]
----
// before
addView<MyConfig>("MyView", CustomView);

// after, the config type is inferred
addView("MyView", CustomView);
----

=== withModel and withModelLoader Are Guarded Features

Both mark their feature as configured and reject a config that already has it. Installing either twice, or a custom model loader together with `withPlatformModelLoader` or `withHTTPModelLoader`, is now a compile error.

Required:: Depending on whether you configured a model or a model loader more than once.
Migration:: Manual, no codemod available.
Result::
+
[source,typescript]
----
// before, the later call silently won
combineFeatures(withModelLoader(myLoader), withPlatformModelLoader);

// after, keep one model and one model loader per setup
combineFeatures(withModelLoader(myLoader));
----

=== View and Layout Registrations Are Composed Once

View and layout modifications were re-applied on every render, so each region change re-mounted every modified view. Registrations are now plain data, composed once when `createA12ApplicationSetup` runs. The `ProviderConfig` fields holding them changed their type:

|===
| Field | Old Type | New Type
| views | `(name: string) => View.ViewComponent \| undefined` | `Readonly<Record<string, View.ViewComponent>>`
| viewModifications | `(name: string) => ((v: View.ViewComponent) => View.ViewComponent) \| undefined` | `readonly ViewModification[]`
| layouts | `(name: string) => Layout \| undefined` | `Readonly<Record<string, Layout>>`
| layoutModifications | `(name: string) => ((l: Layout) => Layout) \| undefined` | `readonly LayoutModification[]`
|===

`addView`, `modifyView`, `addLayout` and `modifyLayout` keep their signature, so code using only the builders compiles unchanged. Behavior differs in three ways:

* A modification function is called once per name at setup, not on every render.
* `modifyView` only modifies views registered with `addView` or built in. Views provided by a registered module are no longer modified.
* A modification for a name without a view or layout has no effect and logs a warning in development.

Required:: Depending on whether you read or assign these fields directly, or modify views provided by a module.
Migration:: Manual, no codemod available.
Result::
+
[source,typescript]
----
// before
const MyView = config.views?.("MyView");
const cfg = { ...config, views: (name: string) => (name === "MyView" ? CustomView : undefined) };

// after, read the record, and register with the builders
const MyView = config.views?.["MyView"];
const cfg = addView("MyView", CustomView)(config);
----

== Other Changes

=== Own Application Model Kept Next To The App Model Adapter

`withAppModelAdapter` wrote `APPLICATION_MODEL_PLACEHOLDER` unconditionally, so `combineFeatures(withModel(myModel), withAppModelAdapter)` lost `myModel`, while the other order kept it. The placeholder is now only written when no Application Model is configured, and both orders keep your model.

Required:: No
Migration:: Not needed
Result:: No changes required.
